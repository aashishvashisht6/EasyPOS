## 14. Cash Drawer Integration

Square, Toast, Clover, and Lightspeed all support kicking open a receipt-printer-attached cash drawer automatically after a cash payment completes (the drawer is wired through the printer via an RJ11/RJ12 port, not a separate USB device) — this is standard till hardware, and the trigger is almost always "cash tender confirmed," with an optional manual "open drawer" button for no-sale cash checks. Implementation is universally an ESC/POS command sequence (`\x1B\x70\x00\x19\xFA` or similar) sent to the printer, which is why these products all ship a print-server/agent component (Star/Epson SDK, or a local print bridge) rather than doing it from pure browser JS.

Today's receipt flow in this app is 100% browser `window.print()` via Frappe's printview page (`InvoicePay/index.jsx` opens `/printview?...&trigger_print=1`) — there is no raw ESC/POS channel to a printer at all, so this is not a small addition on top of the existing print flow but a new hardware-integration layer (most realistically WebUSB direct-to-printer, since a browser can't open a serial/RJ11 port; some receipt printers expose ESC/POS over WebUSB/WebSerial with a compatible driver). Scope should start with a "Manual open drawer" button gated behind a new POS Profile flag (mirroring `printReceiptOnOrderComplete`) before attempting "auto-open on cash payment," since the auto path depends entirely on whether the shop's printer hardware exposes a browser-reachable interface at all — this needs a hardware/vendor decision before a real implementation plan, not just a UI decision.

## 15. Keyboard Shortcuts

Nearly every counter-service POS (Square, Toast, Lightspeed, Clover) supports at minimum: a numeric-then-Enter quantity-then-add flow, `F`-key or `Ctrl+`-prefixed shortcuts for common actions (new sale / void line / open payment / apply discount / search focus), and an `?`-triggered shortcut-list overlay — aimed at power cashiers who want to avoid mouse trips during a rush. The barcode-scanner keystroke pattern already in this app (rapid keys + Enter) is a close cousin of this same "the keyboard is the primary input device at a busy till" philosophy.

Extend the existing global-keydown pattern from `posapp/src/hooks/useBarcodeScanner.js` with a new `useKeyboardShortcuts` hook (same `addEventListener`/cleanup shape, same "skip while an editable element has focus" guard) mounted in `POSTerminalPage.jsx` alongside it. A sensible v1 shortcut set: `/` or `Ctrl+K` to focus item search, `F2`/`Ctrl+Enter` to open `InvoicePay`, `Ctrl+Backspace` to void the last cart line, `Ctrl+D` to focus the discount field, `?` to open a small shortcuts-reference modal (reuse `common/Modal`). No backend involvement — this is a frontend-only hook + a static reference modal.

## 16. Cash Movement (Paid In / Paid Out)

Square, Toast, and Clover all support a manager-gated "cash management" action mid-shift — recording cash removed from the drawer (a "drop"/"paid out," e.g. a bank deposit or petty-cash purchase) or added to it (a "paid in," e.g. topping up change) — logged with a reason and timestamp, and folded into the shift's expected-cash calculation at close-out so the till reconciles correctly even when cash moved in/out mid-shift outside of sales. Without this, any manager who has to pull cash mid-shift breaks the closing-count math, which is exactly the gap in this app today (only opening/closing snapshots + invoice payments feed `get_closing_entry`).

Add a new child-doctype, e.g. `EP Cash Movement` (fields: `opening_entry` Link, `movement_type` Select [`Cash In`/`Cash Out`], `amount`, `reason`, `time`), created via a small modal (a "Cash In/Out" button near Closing/Opening, using existing `common/CurrencyField`/`common/TextField`/`Modal` patterns) that inserts a row against the cashier's active `EP Opening Entry`. `get_closing_entry` (`easy_pos/api/pos.py`) then needs to sum these movements per mode of payment (cash only, realistically) into its existing `closing_amount_dict` alongside the current `Sales Invoice Payment` aggregation — same `frappe.qb` pattern already used there, just one more grouped sum merged in.

## 17. Kitchen Display System (KDS)

KDS is standard in food-service POS (Toast, Square for Restaurants, and especially Petpooja/Posist in the Indian F&B market this app likely targets) — on submitting an order, line items route to one or more kitchen-station screens (or a KOT ticket printed at the kitchen printer) showing item, qty, modifiers, and table/order reference; kitchen staff mark items "Preparing" → "Ready," which can feed back to the front-of-house (e.g. a "your order is ready" cue). It's a genuinely separate real-time display, usually its own device/tablet in the kitchen, and is the single largest feature of this batch — much closer in scope to a small sub-project than a quick add.

This is fully greenfield in this app — no order-routing, item-group-to-station mapping, or per-item prep-status concept exists anywhere today. The closest reusable scaffolding is (a) the invoice-creation pipeline in `easy_pos/api/pos.py` (`_save_sales_invoice`/`create_invoice`) as the natural point to also create a lightweight "KOT" doctype per submitted invoice (or per Item Group, if routing to multiple stations), and (b) the same-origin `BroadcastChannel` approach shipped for the Customer-Facing Display (#3, `customerDisplayChannel.js`) as a same-machine transport if the kitchen screen is just another window on the LAN — though a real multi-device kitchen screen (a genuinely separate tablet, not a second monitor on the register PC) would need Frappe's realtime/socketio instead, same caveat noted for the Customer Display's future "separate device" mode. This should get its own dedicated planning pass rather than being scoped inline here, given its size (comparable to #12 Offline & Sync in complexity, not a one-file feature).

## 19. Multi-Currency Support

Support a POS estate that isn't single-currency top to bottom — e.g. a business with POS Profiles/Companies in different currencies, or wanting to price/display in a currency other than the shop's base currency. This app's currency model today is **single-currency, single-shift, by construction**, not just "untested for multi-currency": `posSessionStore.js`'s `loadProfileDetails(pos_profile)` resolves `currencyCode`/`currencySymbol` exactly once per Opening Entry, straight from the chosen POS Profile's `currency` field (falling back to a hardcoded `DEFAULT_CURRENCY = "INR"`/`DEFAULT_SYMBOL = "₹"` only if the profile has none set), and that resolution sticks for the entire shift — there is no per-transaction, per-line, or mid-shift currency selection anywhere in the Terminal/Cart. Backing this up, `easy_pos/api/pricing.py` hardcodes `"conversion_rate": 1, "plc_conversion_rate": 1` in the args passed to ERPNext's own price/tax resolution helpers — the only two exchange-rate-shaped values anywhere in this codebase, and both are pinned to "no conversion happens, ever." `_save_sales_invoice` (`easy_pos/api/pos.py`) never sets `currency`/`conversion_rate` on the Sales Invoice it builds, relying entirely on ERPNext's own controller to default it from the profile/customer/company — which works fine for single-currency shops but has no cross-currency awareness to fall back on. `_get_rate_map` (`easy_pos/api/item.py`) fetches `Item Price` rows filtered only by `item_code`/`price_list`/`selling`/validity — no `currency` filter — so it silently assumes the selected Price List is itself single-currency (true today, but an unenforced assumption, not a guarantee).

A real implementation needs to decide the actual use case first (is this "different Companies/Profiles in different currencies, cashier picks one at login" — already mostly supported structurally, since a POS Profile is Company-scoped in ERPNext — or "a single till needs to price/accept payment in a second currency," which is a much bigger lift requiring live exchange rates, dual-currency payment rows, and rounding rules)? Two smaller, real bugs surface regardless of scope decision and are worth fixing either way: (a) two spots bypass the store's resolved `currencySymbol` entirely with a literal hardcoded `₹` — `posapp/src/components/Cart/DraftPickerModal.jsx` and `posapp/src/pages/InvoiceRegisterPage.jsx`; (b) **ten** `formatAmount`-style helpers across the app (`Closing/index.jsx`, `CashMovement/index.jsx`, `Cart/index.jsx`, `InvoicePay/index.jsx`, `InvoiceDetailPage.jsx`, `ReportsPage.jsx`, `Invoice/CreditNoteModal.jsx`, and all three `CustomerDisplay/*.jsx` views) call `.toLocaleString("en-IN", ...)` unconditionally — so a shop whose POS Profile currency is USD/EUR already gets Indian lakh/crore digit-grouping on its totals today, a live display bug independent of any future multi-currency scope, that should be fixed by deriving the locale from `currencyCode` (or using `Intl.NumberFormat(undefined, { style: "currency", currency: currencyCode })`) at each call site.

## 20. Multi-Lingual POS (i18n / Localization)

Let cashiers/customers see the Terminal UI in a language other than English — relevant for this app's likely Indian F&B/retail target market (Hindi, regional languages) as well as any international deployment. Today there is **no i18n layer of any kind**: `posapp/package.json` has no `react-i18next`/`react-intl`/`i18next` dependency at all, and grepping the entire `posapp/src` tree for `useTranslation`, `i18next`, or `frappe.__`/`__(` returns zero matches — every button label, placeholder, header, and error/validation message across all ~67 `.jsx` files under `pages/`+`components/` is a raw hardcoded English string baked directly into JSX. A rough scope check (attribute-level `placeholder=`/`label=`/`title=` strings plus inline JSX text nodes) turns up **300–450+ distinct hardcoded strings** — this is a broad, every-file-touches-it first pass, not a contained feature, closer in shape to the Dark Mode rollout's scope but on strings instead of colors. Frappe itself ships a framework-wide translation system (`frappe.__()`, the `Translation` doctype, `bench get-untranslated`/`update-translations`) that the desk UI already benefits from, but `posapp/` is a fully custom Vite-built SPA that doesn't load or call into any of it today — so this app would need its own client-side i18n stack (most realistically `react-i18next` with JSON message catalogs bundled at build time, optionally seeded/kept in sync with Frappe's own `Translation` doctype rather than maintained as a fully separate set of translation files) rather than getting translations "for free" from the framework underneath it.

Two supporting gaps worth flagging up front rather than discovering mid-implementation: (a) neither `authStore.js` nor `posSessionStore.js` reads the logged-in user's `language` field today (a standard field on Frappe's own `User` doctype) — a "default to the cashier's configured language" auto-detect would need this wired in, on top of (or instead of) a manual in-app language switcher (the natural place being next to the existing dark-mode toggle in `Topbar`, following that toggle's own `localStorage`-persisted, device/shift-scoped pattern rather than a account-wide setting); (b) the theme layer (`theme/tokens.css`/`theme/components.css`) has zero RTL consideration — no `dir=`/`rtl`/logical-property (`margin-inline`, etc.) usage anywhere — so this is fine as scoped for any LTR language (Hindi, regional Indic scripts, European languages) but would need a dedicated CSS audit/rewrite before Arabic/Hebrew/Urdu could be supported; that audit is out of scope unless RTL languages are explicitly part of the target list. Suggested phasing: (1) stand up `react-i18next` + an English baseline catalog extracted from the current hardcoded strings (mechanical but large, touches nearly every component file), (2) add one additional language end-to-end (proving the pipeline, catching interpolation/pluralization edge cases in receipts/toasts), (3) the `Topbar` language switcher + optional `User.language` auto-detect, deferring RTL entirely to a future pass if ever needed.
