# Offline-First POS — Implementation Plan

Status: **Phases 1 and 2 of 3 shipped (2026-10-21)**; Phase 3 is partially done and now considered **closed at its current scope** — see its section below for exactly what's wired, what isn't, and why opening/closing shifts stay online-only by design rather than an open gap. This is the working plan for [UPCOMING_FEATURES.md](UPCOMING_FEATURES.md)'s item #12 (Offline & Sync) — kept as its own doc rather than folded into that one-paragraph entry because the feature spans multiple sessions and needs a durable record of what shipped, what's next, and the gotchas hit along the way.

## Context

Target architecture (per [`CLAUDE.md`](../CLAUDE.md)) is offline-first; the shipped build was online-only, and `SyncPage.jsx` was an explicit UI-only mock (hardcoded doctype list, fake pending counts, `setTimeout`-faked buttons). Before this plan started, the team had already landed real scaffolding for it — `posapp/src/engine/{index.js,db.js,settingsStore.js}` — which intercepts every `api/*.js` call through `engineGet`/`enginePost` instead of raw axios, gated by an `EASYPOS Settings.enable_offline_mode` checkbox. But the local-DB branch was a stub: `readFromLocalDB()` just threw, and Dexie's tables were primary-key-only schemas that were never written to. This plan finishes that scaffolding, screen by screen: **master data → transactional data → POS terminal screen**.

### Decisions locked in

- **Connectivity model**: auto-detected, not a manual toggle. `enable_offline_mode` gates whether the *capability* exists for a deployment; a separate live connectivity store decides online vs. offline moment-to-moment (browser `online`/`offline` events + a periodic heartbeat ping to the server, since a till can report "online" to the OS while the site itself is unreachable, and vice versa on some networks).
- **Conflict policy** (for Phase 2's queued writes): queue + manual review. A write that fails server-side validation on replay goes to a "needs review" queue visible on the Sync page — never silently dropped or auto-overwritten. Successful syncs happen automatically in the background.
- **Pacing**: each phase is implemented and verified end-to-end before moving to the next, across separate sessions rather than attempting all three at once.

## Phase 1 — Master Data Offline — ✅ Shipped (2026-08-08)

Doctypes: Item, Item Group, Customer, Price List, Pricing Rule, Sales Taxes and Charges Template, POS Profile, Mode of Payment — exactly the `OFFLINE_CAPABLE_DOCTYPES` already named in `engine/index.js` before this phase.

### What shipped

- **Backend** — `easy_pos/api/sync.py`: `get_offline_snapshot(pos_profile)`, one whitelisted call that reuses the *existing* resolution helpers (`easy_pos.api.item.get_items`, `easy_pos.api.item.get_item_groups`, `easy_pos.api.pos.get_taxes_and_charges_template`) instead of re-deriving stock/rate/tax math in JS — the cached item rows are exactly what the terminal would already see live, for the profile's own warehouse/price list. One deliberate simplification: resolution runs with no `customer`, so a cached item's rate is the generic (non-customer) price-list rate; a customer-specific price only ever applies once one is picked in the cart, which needs the server anyway.
- **`posapp/src/engine/db.js`**: Dexie schema, now at v3 (see the migration gotcha below for why it isn't v2).
- **`posapp/src/engine/connectivity.js`** (new): `useConnectivityStore` — `isOnline`, updated by `window.addEventListener('online'/'offline')` plus a ~30s heartbeat to Frappe's built-in `ping` endpoint (bypasses the engine layer entirely — a heartbeat must never itself be routed to the local DB).
- **`posapp/src/engine/sync.js`** (new): `runFullSync(posProfile)` — fetches the snapshot, bulk-writes every Dexie table in one transaction, stamps a `meta.lastSyncedAt` per domain. Also `getDomainCounts`/`getLastSyncedTimes` for the Sync page. Triggered (a) automatically, fire-and-forget, once per shift-open when online (`posSessionStore.loadProfileDetails`), and (b) manually via the Sync page's Fetch button.
- **`posapp/src/engine/localReads.js`** (new): a small adapter registry that pattern-matches each call's `url`/`params`/`data` (the exact shapes `api/Items.js`, `api/ItemGroup.js`, `api/Customer.js`, `api/POSProfile.js`, `api/PriceList.js`, `api/PricingRule.js`, `api/Tax.js` already send) and serves the equivalent result from Dexie. Only the read shapes actually exercised by the Terminal/shift-load hot path are covered — anything else has no adapter and throws loudly instead of silently returning nothing.
- **`posapp/src/engine/index.js`**: rewritten so offline routing is based on *live connectivity* (not just the settings flag) and *never applies to writes* — a small `WRITE_METHOD_MARKERS` list (`client.insert`, `client.save`, `client.delete`, `client.submit`, `client.cancel`, `pos.create_`, `pos.cancel_`) keeps every write going to the server, where it'll simply fail with a network error while offline until Phase 2's write queue lands.
- **`posapp/src/pages/SyncPage.jsx`**: replaced every hardcoded mock with real state — per-domain row counts and `lastSyncedAt` read from Dexie, a working Fetch button, and the connectivity pill wired to `useConnectivityStore`.

### Known limitations (by design, deferred to a later pass)

- **No barcode offline *search*** — `ITEM_FIELDS` (and thus the cached snapshot) only carries `item_code`/`item_name`, not barcode rows, so a scanned/typed barcode can't resolve to an item offline, only an exact item code or a fuzzy code/name substring. A future snapshot revision would need to fold in `Item Barcode` rows. (This is distinct from *assigning* a serial/batch number to an item already in the cart, which is covered below — Serial No/Batch No themselves are cached.)
- **No item-group hierarchy offline** — the cached `item_groups` table doesn't carry `parent_item_group`, so filtering by a parent group only exact-matches that one group offline, instead of expanding to its descendants the way `get_items` does live.
- Calls with no adapter (`fetchItemVariants`, `fetchProductBundleContents`, `fetchCustomerGroups`/`fetchTerritories`, `fetchProfilesForCompany`, `fetchCompanyDefaults`, `fetchItemUoms`, `fetchItemsValidationData`, ...) simply fail offline — acceptable for Phase 1 since none of them are on the Terminal's core add-to-cart path.
- Customer cache is capped at 2000 rows (`MAX_CACHED_CUSTOMERS` in `easy_pos/api/sync.py`) — most-recently-modified first — not a shop's entire multi-year customer history.

### Follow-up pass (2026-10-21) — serial/batch items, and a pricing-rules caching gap

A dedicated test pass covering offline invoice creation across every item type (plain stock, serial-tracked, batch-tracked, and a genuine non-stock service item) and Pricing Rule/Price List/Item Price resolution found and fixed two real gaps, plus surfaced one inherent risk worth knowing about:

- **Fixed — Serial No / Batch No couldn't be assigned offline at all.** `Cart/index.jsx`'s per-line Serial No / Batch No fields are `LinkField`s (autocomplete only — no free-text commit path), which call `frappe.desk.search.search_link` for doctype `Serial No`/`Batch`. Neither had a cached data source or a `localReads.js` adapter, so offline the dropdown always came back empty — a serial/batch-tracked item could be added to the cart (the `has_serial_no`/`has_batch_no` flags came through fine) but could never actually have a number assigned to it, which would have failed validation the moment the queued invoice synced. Fixed by adding `serial_nos`/`batches` as new cached domains (`easy_pos.api.sync.get_offline_snapshot`, scoped to only the catalog's own serial/batch-tracked items — see `SERIAL_NO_FIELDS`/`BATCH_FIELDS`), new Dexie tables (`db.js` v6), and `SEARCH_LINK_SOURCES` entries in `localReads.js` that replay the exact same `{item_code, status, warehouse}` / `{item, disabled}` filters the live `search_link` call uses. Verified end-to-end: added a serial-tracked and a batch-tracked item to an offline cart, assigned real numbers from the offline dropdown, checked out, reconnected, pushed, and confirmed the resulting Sales Invoice carried the correct `serial_no`/`batch_no` and submitted cleanly (the serial's stock status correctly flips `Active` → `Delivered` → back to `Active` on a test cancel).
- **Fixed — Pricing Rule discounts silently reset to zero on any reload while offline.** `posSessionStore.loadProfileDetails` calls `fetchPricingRules` (`easy_pos.api.pricing.get_pricing_rules`) every time it runs — not just once at shift-open, but on every page load/refresh via `checkOpeningEntry`. `fetchPricingRules` had no offline adapter and its own `catch` block silently returned `[]` on failure, so a page reload while offline mid-shift (recovering from a crash, an accidental refresh) wiped every Item Code/Item Group discount rule from the Cart's client-side pricing engine until reconnection — even though the shift itself was still perfectly valid. Fixed the same way the existing `openingEntry`/`loggedInUser` caches work: `fetchPricingRules` now also writes its successful result to `db.meta` (`pricingRules:<pos_profile>`), and a new `localReads.js` adapter serves it back offline. Verified: a 10%-off Item Group rule applied correctly client-side offline, and survived being read from cache.
- **Known risk, not fixed — a Product Discount (free item) Pricing Rule in the cart silently drops *every* line's pricing to list price while offline, cart-wide, not just the matching line.** `utils/pricingEngine.js`'s `computeCartPricingLocally` can only resolve Price-type rules (rate/discount-percentage/discount-amount); the moment *any* cart line matches a Product Discount rule, it returns `null` for the **entire** cart in one shot, and the caller falls back to `easy_pos.api.pricing.get_cart_pricing` — which has no offline adapter and can't succeed without a connection. Previously this failed completely silently (no error, no visual difference — the cashier would see list-price totals with no indication why a discount vanished). Now surfaced with a visible notice in the Cart ("A free-item offer in this cart needs a connection to resolve…"), but the underlying resolution gap remains: **the amount actually collected from the customer at the register (based on the undiscounted preview) can end up higher than the invoice's final `grand_total` once pricing rules correctly re-apply server-side on sync** (ERPNext's own Sales Invoice controller re-evaluates Pricing Rules on `insert()` regardless of what the client sent, which is actually reassuring for ledger correctness — the invoice itself always ends up right, recording the difference as `change_amount` — but that money was never physically handed back to the customer in the moment, since the till's own screen showed a higher total as fully paid with zero change due). Fixing this properly means either blocking checkout entirely when a Product Discount rule can't resolve offline, or accepting the plain price-list total as authoritative and preventing the server from silently re-pricing a POS-sourced invoice on sync — a product decision, not a quick patch, so left as a documented risk rather than attempted here.

### Pricing-parity pass (2026-10-26) — offline pricing now mirrors ERPNext

Driven by a browser test run (agent-browser) comparing the offline engine against `get_cart_pricing` over 420 cart scenarios; all 390 locally-resolvable ones now match (the other 30 involve a rule with a Python `condition`, which deliberately defers to the server).

- **`utils/pricingEngine.js` rewritten** as a port of ERPNext's rule selection (`pricing_rule/utils.py` `get_pricing_rules` / `filter_pricing_rules`, `apply_price_discount_rule`, `get_product_discount_rule`): Item Code → Item Group → Brand lookup order, text-priority ordering, qty/amount bands, currency preference, tie conflicts (no discount + ERPNext's message, instead of a zero price), `apply_multiple_pricing_rules` stacking, `apply_discount_on_rate`, coupon-based rules, and Product Discount free items (incl. recursive). The previous "any free-item rule → whole cart unpriced offline" gap is closed.
- **`get_pricing_rules` snapshot widened**: blank-company rules, Brand rules, coupon rules (with their Coupon Code rows), item-group / customer-group / territory subtrees pre-expanded, and a `needs_server` flag for features not modelled (mixed conditions, cumulative, `apply_rule_on_other`, Python `condition`, margins, UOM-pinned rows). A cart containing a flagged rule can't be priced offline: the Cart blocks **Pay** (Save Draft stays available) rather than collecting an amount the server will later change.
- **Offline customer group/territory**: `get_customer_with_loyalty` now has a `localReads` adapter (last online result, else the synced customer row), so group/territory-scoped rules apply offline.
- **Cart fixes found by the run**: re-selecting the same customer no longer clears group/territory; switching customers reprices from the catalog price (`base_price_list_rate`) instead of compounding a previous "Rate" rule; resuming a draft restores `price_list_rate`/`item_group`/`brand` (resumed lines used to price from ₹0).
- **Outbox**: `push_offline_invoice` now upgrades an already-pushed Draft when the queued row was later paid (it used to return the stale Draft, leaving a paid sale unsubmitted); a push cut off by a dropped connection re-queues instead of sticking in `syncing`/`failed`; the snapshot refreshes on reconnect.
- **Server**: `get_cart_pricing` passes the cart as a document (recursive rules), survives `MultiplePricingRuleConflict` by pricing that line with no rule plus a message, and no longer returns price 0 on a rule error.
- **Known, not changed**: ERPNext rounds the grand total (e.g. ₹261.60 → ₹262) while the till collects the unrounded amount, leaving a small outstanding balance on the invoice.

### Gotchas hit while building this (worth knowing before touching this code again)

- **`EASYPOS Settings` is the doctype's real name** (all caps), despite the field label reading "EasyPOS Settings" — `frappe.db.set_single_value("EasyPOS Settings", ...)` silently no-ops against a doctype that doesn't exist by that exact casing.
- **Dexie cannot change an existing table's primary key in place.** The original `db.js` had `items`/`item_groups`/`taxes` keyed by `"name"` (an empty, never-written-to stub). Declaring a v2 that changes their key straight to `item_code`/`item_group`/`template` throws `"Not yet support for changing primary key"` on any browser that already has the v1 database open — which then **closes the whole database**, cascading into `DatabaseClosedError` on every subsequent call. Fixed by splitting the migration across two versions: v2 drops the three affected tables (`null` in `.stores()`), v3 recreates them with the new key. Any future primary-key change on an existing table needs the same drop-then-recreate two-step, never a direct key change in one version bump. Verified by reproducing the exact scenario — a raw IndexedDB built to the original shipped v1 schema with real data in an unaffected table — and confirming a normal page load migrates it cleanly with no manual intervention.
- **Custom whitelisted methods (`get_items`, `search_item`, `get_item_groups`, `get_taxes_and_charges_template`, ...) have no `doctype` param for `engine/index.js`'s old doctype-extraction logic to find** — only generic `frappe.client.*` calls do. The original stub's `isOfflineCapable(doctype)` approach would never have routed these hot-path calls locally at all. Fixed by dropping doctype-extraction entirely in favor of asking `localReads.js` directly ("does an adapter exist for this exact call shape?") — capability is now defined by what's actually implemented, not by a doctype allowlist that doesn't match how these endpoints are called.

### Verification performed

- Backend: `get_offline_snapshot` exercised directly via a throwaway `bench execute` script (deleted after) against `easy_pos_site.local`, confirmed correct counts for every domain.
- Frontend: confirmed auto-sync on shift-open populates Dexie with matching counts (visible on the Sync page); confirmed that forcing the connectivity store offline makes an item/customer search resolve from cache with **zero** network calls; confirmed the Dexie migration fix against a reproduction of the exact pre-existing-v1-database failure scenario.

## Phase 2 — Transactional Data Offline — ✅ Shipped (invoice queue; opening/closing/customer writes deferred)

Shipped scope: `create_invoice` (draft + submit) only. Opening/closing entries and `createCustomer`/`createAddress`/`createContact` were in the original plan but were **not** built in this pass — see "Known gaps" below.

### What shipped

- **`posapp/src/engine/outbox.js`** (new) — the offline write queue. Backed by Dexie's `pending_invoices` table (`db.js` v5: `offline_id, status, created_at`), not a generic `pending_mutations` table as originally sketched — invoice queuing turned out to need enough invoice-specific shape (a client-generated `offline_id` *and* a cashier-facing `display_id` like `OFFLINE-20261021143000-482`, a `sanitizeInvoicePayload` step, an `upsertInvoiceCache` step on success) that a generic envelope would've just been unwrapped immediately anyway.
  - `queueOfflineInvoice`/`updateQueuedInvoice` — called from `engine/index.js`'s `engineCall` instead of failing when `create_invoice` is hit offline; `updateQueuedInvoice` re-saves an already-queued row in place (resuming a held offline draft) instead of queuing a duplicate.
  - `pushPendingInvoices` — drains every `queued` row oldest-first (preserves ring-up order, matters for stock deduction), sequentially. Triggered on the `online` transition (`connectivity.js`'s `setOnline`) and the Sync page's manual "Push now".
  - `retryOfflineInvoice` — manual per-row retry for a `failed` row; failed rows are deliberately excluded from the automatic drain so a bad invoice doesn't loop on every reconnect.
  - Backend counterpart: `easy_pos.api.sync.push_offline_invoice` replays a queued invoice through the *same* `_save_sales_invoice`/`_finalize_invoice` helpers a normal checkout uses, and is idempotent on `ep_offline_id` (handles both "already pushed, response lost" and the concurrent-push race via `frappe.UniqueValidationError`).
- **Held/parked sales**: `DraftPickerModal` (`components/Cart/DraftPickerModal.jsx`) now merges locally-queued offline drafts (`getPendingInvoices`) alongside live server Drafts, badged "Held offline — not yet synced" (or the failure reason, if a push attempt already failed). `Cart/index.jsx` resumes a queued draft via `updateQueuedInvoice` rather than treating it as a normal fetched doc — this was the one piece of the original Phase 2 plan that got explicit, implemented special-casing exactly as flagged above.
- **Sync page** (`SyncPage.jsx`): a "needs review" list of non-synced queue rows with status badges (`Queued`/`Syncing…`/`Failed`/`Synced`), a manual "Push now" for the whole queue, and a per-row Retry for failed ones — fulfills the conflict-policy decision from the top of this doc (queue + manual review, never silently dropped or auto-overwritten).

### Deliberate scope boundary: shift open/close stay online-only

`create_opening_entry`/`create_closing_entry` were prototyped as a queued-offline flow in an earlier pass of this session (mirroring `outbox.js`'s invoice queue, with a placeholder `OFFOPEN-`/`OFFCLOSE-` name resolved to the real ERPNext name on reconnect) and verified working end-to-end — but then deliberately reverted. The reason: `easy_pos.api.sync.get_offline_snapshot`'s cached item rows (`items` table) are resolved with a **specific POS Profile's own `warehouse`/`selling_price_list`** baked in at sync time (see Phase 1 above) — there is no warehouse-agnostic item cache to fall back to. A shift opened fully offline for a profile that was never synced online before (or was synced under a *different* profile's warehouse during the last `runFullSync`) would show wrong, stale, or missing stock/rate with no way to re-resolve it without connectivity — exactly the kind of silent data-correctness bug this app's existing gotchas warn against. Letting a cashier open a shift against bad stock data is worse than just requiring connectivity to open one.

So: **opening and closing a shift always requires being online**, same as `createCustomer`/`createAddress`/`createContact` and every other write not named in `outbox.js`. Only mid-shift transactions (ringing up and holding sales — `create_invoice`, already synced to the right warehouse by the time the shift opened) are safe to queue offline, because by definition the shift's stock/pricing was already correctly resolved before the connection dropped. `OpeningEntryModal.jsx` shows an explicit "Opening a shift requires an internet connection…" notice and disables its submit button when `offlineModeEnabled && !isOnline`; `Topbar`'s "Close shift" button is disabled the same way.

- **`createCustomer`/`createAddress`/`createContact` are not queued either** — walk-in/new-customer creation still requires connectivity (same reasoning doesn't strictly apply here, it just wasn't built — a smaller, independently pickable gap if ever prioritized).
- **No offline PIN login** — a logged-out cashier can't authenticate at all without reaching the server (named in the README roadmap, not started). Note this is different from the offline-boot fallback below: an *already* logged-in session survives opening the app offline; a cashier who is logged *out* still can't sign in without connectivity.

## Phase 3 — POS Terminal Screen — ✅ Shipped (within this scope boundary)

### What shipped

- **Gateway-aware payment rows**: `InvoicePay/index.jsx` reads `useConnectivityStore`'s `isOnline` to disable/relabel any `ep_payment_gateway` payment row while offline (badge reads "`<gateway>` — offline", row disabled) instead of letting a cashier attempt a gateway checkout with no connection.
- **Invoice detail retry-sync**: `InvoiceDetailPage.jsx` also reads `isOnline` to disable its "Retry sync" action (and flag `offlineUnavailable`) when there's no connection to retry against.
- **Cart pricing already degrades gracefully offline without special-casing**: the common discount case (`computeCartPricingLocally` in `utils/pricingEngine.js`) resolves entirely client-side against the pricing-rule snapshot `posSessionStore` already holds from shift-open — no server round-trip needed, online or off. Only a coupon code or a Product Discount rule the local engine can't resolve falls through to `get_cart_pricing`, which has no offline adapter and will fail in that narrower case.
- **Offline-boot fallback already existed and was verified, not missing as an earlier pass of this doc claimed**: `api/User.js`'s `fetchLoggedInUser` and `api/OpeningEntry.js`'s `fetchOpeningEntry` both cache their result to `db.meta` (`loggedInUser` / `openingEntry:<user>` keys) on every successful online call, and `engine/localReads.js` has adapters (`readLoggedInUser`, `readCheckOpeningEntry`) serving those same keys back when offline — so `authStore.checkSession()` and `posSessionStore.checkOpeningEntry()` both resolve correctly even if the app is opened (or refreshed) while *already* offline mid-shift, as long as that user/shift was seen at least once while online on this device. `main.jsx` awaits `initEngine()` (opens Dexie, loads the offline-mode flag) before the app ever mounts, so this isn't a race.
- **Global online/offline indicator in `Topbar`**: a pill (next to the shift-status pill) showing "Online"/"Offline", gated on `offlineModeEnabled` so it doesn't clutter deployments that don't use the feature.
- **Cached-data banner on `POSTerminalPage`**: "Offline — showing cached catalog and pricing…" shown above the item grid under the same gate, so a cashier isn't left guessing whether they're looking at live or cached data.

### Still not done (minor, non-blocking)

- **`Items`/`Cart`'s silent catch-and-swallow fetch failures don't surface a per-request "using cached data" state** — the Terminal-wide banner above covers the common case; a finer-grained per-field indicator was judged unnecessary scope beyond that.
- **Loyalty summary has no offline fallback** — `fetchCustomerWithLoyalty` (customer doc + points balance) just fails silently offline; the points badge disappears rather than showing a cached balance. Not checkout-blocking, just a missing display.

## Next step

The offline core is functionally complete for its decided scope: a shift must be opened and closed online (correctness boundary, see above), but once open, a cashier can browse the cached catalog, ring up sales, hold/resume drafts, and have everything sync automatically on reconnect — all surfaced clearly via the Topbar pill, the cached-catalog banner, and the Sync page's pending-invoice queue. Remaining items are smaller and independently pickable if ever prioritized: offline PIN login, offline customer/contact/address creation, and a cached-balance fallback for the loyalty summary.
