# EASY POS — Project Instructions

React POS frontend (`posapp/`) for ERPNext/Frappe, packaged as the `easy_pos` Frappe app. Target architecture is offline-first (RxDB/IndexedDB local storage, background sync), but the current build is online-only — see the `SyncPage` gotcha below before assuming any offline/sync code exists.

## Stack & layout
- Frontend: React 19 + Vite 7, React Router 7, Zustand 5 (no Redux/Context for global state), Bootstrap 5 + Bootstrap Icons for styling (no Tailwind/MUI).
- `posapp/src/api/*.js` — one file per Frappe doctype/domain, thin wrappers around `frappe.client.*`, `frappe.desk.reportview.get_list`, `frappe.desk.search.search_link`, or custom whitelisted methods in `easy_pos/api/*.py`. Always add new backend calls here, never call Frappe endpoints directly from components.
- `posapp/src/components/common/` — shared field/layout primitives: `Modal`, `ConfirmModal`, `AlertModal`, `FieldShell`, `TextField`, `NumberField`, `CurrencyField`, `SelectField`, `CheckboxField`, `DateField`, `LinkField`, `ListTable`, `FormView`, `DetailField`, `ChildTable`, `PageLoader`, `PageHeader`, `ErrorAlert`, `SaveButton`. Always reuse these for new forms/modals/detail pages instead of raw `<input>`/bespoke markup. Export new common components via `common/index.js`.
- `posapp/src/store/` — Zustand stores: `authStore`, `cartStore`, `posSessionStore`. Session-wide state (opening entry, currency symbol, pos profile) lives in `posSessionStore`; cart/payment state lives in `cartStore`.
- `posapp/src/theme/` — `tokens.css` (CSS variables: colors, spacing, radius, fonts) + `components.css`. Always use `var(--color-*)`, `var(--font-*)`, `var(--radius-*)` tokens instead of hardcoded values.
- `posapp/src/pages/` — routed pages (`routes.jsx`); `components/` — feature components (Cart, Closing, Opening, InvoicePay, Customer, Items, ItemGroup, Sidebar, Topbar, Layout).
- `posapp/src/components/Sidebar/index.jsx` — `NAV_ITEMS` array drives the left rail. Each primary feature (Terminal, Invoices, Customers, POS Profiles, ...) gets its own dedicated icon/route — don't nest a primary feature under the Settings gear. The gear (`pages/SettingsPage.jsx`) is a landing page of cards for secondary/administrative sections (e.g. future user management) that don't warrant their own top-level icon, not a shortcut to a single existing feature.
- Backend: `easy_pos/api/{pos,auth,customer,item}.py` — whitelisted methods called from the frontend `api/*.js` files.

## Build/dev commands
- Dev server: `cd posapp && yarn dev`.
- Build (also copies built HTML into the Frappe app): `cd posapp && yarn build`.
- Lint: `cd posapp && npx eslint <files>` (or `npx eslint .` for everything) — run this after any JS/JSX edit.
- Bench: `bench --site <site> execute <module>.<function>` for one-off backend scripts/investigation; write temp scripts under `easy_pos/patches/`, run, then delete — don't leave throwaway scripts committed. `bench console` heredocs with indented blocks are unreliable; prefer a temp script + `bench execute`.

## Conventions & gotchas (learned the hard way)
- **Source of truth for payment modes is the POS Profile's `payments` child table, fetched live** (`fetchProfile`), never a POS Opening Entry's `balance_details` snapshot — the snapshot only contains modes the cashier actually typed an amount into at shift-open, so newly added profile payment modes can silently go missing downstream. Both `get_closing_entry` (backend) and `InvoicePay` (frontend) must derive available modes this way.
- **`FieldShell`'s wrapper (`.pos-field`) has a default `margin-bottom: 14px`.** This is a recurring source of misalignment when a common field sits next to plain text/buttons in the same flex/grid row — the margin gets included in box-height calculations even when visually you expect a shared baseline.
  - A field's `className` prop only reaches the inner input/wrapper, **not** the outer `FieldShell`/`.pos-field` div — `className="mb-0"` on a field does nothing to fix this; you must target `.pos-field` margin directly in CSS, or restructure so the action element lives inside the same `.input-group` as the field (see `LinkField`'s `actionIcon`/`actionTitle`/`onAction` props for the pattern of adding an in-row action button correctly).
  - Box top/bottom alignment (`align-items: start/end`) is **not sufficient** to guarantee visual/text alignment when sibling elements have different heights and different internal text-centering behavior (an `<input>` vs. a plain `<div>`). Fix by giving both a matching `min-height` **and** `display:flex; align-items:center` so text is centered identically in both.
  - Verify alignment fixes with `getBoundingClientRect()` via the browser JS tool (compare `top`/`bottom`/`height` of the actual rendered boxes) rather than eyeballing — screenshots can be misleading at small offsets.
- Use the shared `Modal` component (`{ open, onClose, title, subtitle, size, children, footer }`) for all new modals rather than hand-rolling Bootstrap modal markup.
- New Frappe doctype writes (e.g. `createCustomer`) follow the existing `frappe.client.insert` pattern already used in `api/POSProfile.js`'s `createProfile`/`saveProfile`.
- Lookup/select lists (Customer Group, Territory, Warehouse, Price List, Mode of Payment, etc.) are fetched via `frappe.desk.reportview.get_list`, matching the convention across all existing `api/*.js` files.
- When a user reports "still not correct" after an alignment/UI fix and includes a screenshot, don't just re-guess — measure the actual rendered boxes (`getBoundingClientRect`) to find the real discrepancy before changing CSS again.
- Flag pre-existing, unrelated backend bugs encountered mid-task (e.g. other installed app errors surfacing during a POS checkout) via `spawn_task` rather than fixing them inline — keep this repo's frontend work scoped.
- **List-view page pattern** (`CustomerListPage`, `POSProfileListPage`): `common/ListTable` for the grid, `common/FilterChips` for status-style toggles, `common/SelectField`/`TextField` for column filters, `common/Pagination` for paging, and the page's topbar search wired via `useOutletContext().setTopbar({ searchValue, onSearchChange, searchPlaceholder })` — search/filter changes reset `page` to 0 and debounce the fetch (~300ms `setTimeout`). Follow this for any new list page instead of hand-rolling a Bootstrap table.
- List-page API functions (e.g. `fetchCustomers`, `fetchProfiles`) route filters/search/pagination through `api/ListView.js`'s `fetchList(doctype, { fields, filters, or_filters, order_by, limit_start, limit_page_length })`, which calls the generic `easy_pos.api.list_view.get_list` backend method and returns `{ data, total_count }`. Use this instead of `frappe.desk.reportview.get_list` when a page needs filtering, `or_filters` (search-across-columns), or a total count for pagination; plain lookup/select lists (dropdown options) still use `frappe.desk.reportview.get_list` directly per the convention above.
- New/Edit forms: a simple create-only form (few required fields, e.g. `NewCustomerModal`) uses the shared `Modal` from the list page. A form with nested/repeatable data (e.g. POS Profile's `payments` child table) is a full routed editor page (`POSProfileEditorPage`) styled with `pos-card`/`pos-btn` and the `common/*Field` components instead of raw Bootstrap markup, reached via the list page's row click and "New" button.
- Avoid raw SQL (`frappe.db.sql`) — use the Frappe Query Builder (`frappe.qb.DocType`, `frappe.qb.update`/`.select`/`.where`, `frappe.query_builder.functions.*` like `IfNull`) or the Frappe ORM (`frappe.get_doc`, `frappe.db.get_value`/`set_value`/`get_all`) instead. Only reach for raw SQL when the query builder genuinely can't express something.
- **POS Closing's manual-vs-automatic entry is controlled per payment mode, not per POS Profile.** `POS Payment Method` (the `payments` child table doctype) has a custom `Check` field `ep_automatically_calculated` (default checked), added/described via `easy_pos/patches/add_pos_payment_method_auto_calculated.py`. `POSProfileEditorPage` renders it as a checkbox + description under each payment row; `ClosingModal` (`components/Closing/index.jsx`) makes a row's "Counted" amount editable when `!row.automatically_calculated`, with no special-casing of cash. This replaced an earlier POS Profile-level `ep_closing_entry_type` Select field — don't reintroduce a profile-wide toggle for this.
- **`get_closing_entry` (backend) scopes its Sales Invoice Payment aggregation to the current shift via `Sales Invoice.custom_ep_opening_entry`** (a `Link` custom field to `EP Opening Entry`, added by `easy_pos/patches/add_sales_invoice_opening_entry.py`, set once at invoice creation in `create_invoice`). Filtering by `pos_profile` alone is wrong — it aggregates every invoice ever raised against that profile across all shifts, not just the shift being closed.
- **`EP Opening Entry`'s link to its closing document is the field `ep_closing_entry`** (a `Link` to `EP Closing Entry`; it was renamed from `pos_closing_entry`). `check_opening_entry` filters on it to find a user's still-open shift. When renaming a doctype field going forward, editing the field's JSON alone does **not** move existing DB data — write a companion patch that copies the old column's values into the new one (see `easy_pos/patches/rename_ep_opening_entry_closing_field.py` for the Query Builder pattern), otherwise every existing record silently reverts to looking "unset"/"still open".
- **Editable detail-page header pattern** (`CustomerDetailPage`, `POSProfileDetailPage`, `DiscountDetailPage`, `PriceListDetailPage`, `ItemPriceDetailPage`, `LoyaltyProgramDetailPage`): these six pages had all hand-rolled an identical full-page loading spinner, back-link header (back arrow + label, title, optional status badge/subtitle), Save button with a spinner+"Saving…" swap while saving, and a plain `alert alert-danger` error banner. That duplication is now factored into `common/PageLoader` (`if (loading) return <PageLoader />;`), `common/PageHeader` (`{ title, subtitle, badge, backTo, backLabel, actions }` — also used internally by `common/FormView` for read-only pages, so both editable and read-only detail pages share one header implementation), `common/ErrorAlert` (`<ErrorAlert message={error} />`, renders nothing when `message` is falsy), and `common/SaveButton` (`{ saving, onClick, label, savingLabel, variant, disabled }`). Use these four for any new detail page or modal instead of re-inlining the spinner/header/alert/button markup — several modals (`OpeningEntryModal`, `ContactModal`, `AddressModal`, `NewCustomerModal`, `InvoicePay`, `CreditNoteModal`) already use `ErrorAlert` for their error banner.
- **Detail/read-only view pattern** (`InvoiceDetailPage`): a routed page (reached via a list page's `ListTable` row click, e.g. `/posapp/invoices/:name`) renders through the generic `common/FormView` component instead of a modal or hand-rolled markup — pass it an ordered `blocks` array where each entry is either `{ type: "fields", title, fields: [{ label, value, mono, muted, span }] }` (rendered via `common/DetailField`) or `{ type: "table", title, columns, rows, footer }` (rendered via `common/ChildTable`). `blocks` is a single ordered list (not separate `sections`/`tables` props) specifically so a page can interleave a child table between two field sections (e.g. Invoice Details → Items table → Additional Discount → Taxes and Charges table). `FormView`/`DetailField`/`ChildTable` are doctype-agnostic — the page component owns fetching the doc and shaping it into `blocks`; `FormView` only lays each block out consistently with the theme (`pos-card` per block, `.pos-detail-label`/`.pos-detail-value` styling). Reuse this instead of the old approach of opening a `Modal` with raw Bootstrap `<table>` markup for record details. Shared display helpers (`formatDate`, `invoiceStatusBadgeClass`) live in `posapp/src/utils/format.js` — prefer adding to/reusing that file over redefining per-page.
- **Grid-table styling is shared between `ChildTable` and `ListTable`** via the `.pos-table-head`/`.pos-table-row`/`.pos-table-footer` classes in `theme/components.css` — uppercase caption headers, zebra striping, a hover highlight per row, and monospaced numeric cells for any column with `align: "end"` or `align: "center"`. Both components set an explicit `columnGap` on their CSS grid rows (not just padding) — omitting it lets adjacent cell text visually run together (e.g. a `—` placeholder butting up against the next column's `—`) since grid columns have no default gutter. When adding a new grid-based table, reuse these classes rather than hand-rolling header/row styling again.
- **Invoice cancel / credit note actions** (`InvoiceDetailPage`, `components/Invoice/CreditNoteModal.jsx`): `common/ConfirmModal` (`{ open, onClose, onConfirm, title, message, confirmLabel, cancelLabel, danger, loading, error }`) is the generic Yes/No confirm pattern — use it for any destructive/confirm-before-acting flow instead of a one-off `Modal`. Cancelling calls `easy_pos.api.pos.cancel_sales_invoice` (just `doc.cancel()`); creating a credit note calls `easy_pos.api.pos.create_credit_note`, which builds a new `Sales Invoice` with `is_return=1`, `return_against=<original name>`, negative item qty, and the taxes the user edited in the modal — then lets Frappe's standard `calculate_taxes_and_totals` recompute amounts against the return's own (negative) net total rather than trusting client-computed totals. Both `cancelInvoice`/`createCreditNote` in `api/Invoice.js` deliberately skip the try/catch-and-swallow pattern used elsewhere in `api/*.js` (which returns `undefined` on failure) so the backend's `frappe.throw` validation message actually reaches the UI — follow this (propagate, don't swallow) for any new API call whose failure needs a user-visible message. "Cancel Invoice" shows whenever `docstatus === 1`; "Create Credit Note" additionally requires `!invoice.is_return` (can't return a return) — mirror both checks before adding new document-level actions to this page.
- **`create_credit_note` must copy `is_pos`, `pos_profile`, and `custom_ep_opening_entry` from the original invoice onto the new return Sales Invoice.** `InvoiceRegister.js`'s `fetchInvoices` hard-filters on `is_pos: 1` for the list page, so a return created without `is_pos` set silently vanishes from the Invoices list even though it exists and is fully valid — this bit us for the first two credit notes created (`ACC-SINV-2026-00009`/`00010`, backfilled via a one-off `frappe.db.set_value` patch since `is_return` docs can't be re-saved through the normal controller). Verify a return posted through the UI actually shows the correct `pos_profile` on `/posapp/invoices` before considering a credit-note-related change done. `validate_pos_return`/`validate_pos_paid_amount` in ERPNext's Sales Invoice controller don't require payment rows on an `is_pos=1` return since its `grand_total` is negative, so setting `is_pos` doesn't break submission.
- **A `ListTable`/`ChildTable` row's inline `style`/`rowStyle` always beats the `.pos-table-row:hover`/zebra CSS rules, even for an unconditional value like `background: "transparent"`.** Inline styles win over stylesheet rules (including `:hover`) regardless of selector specificity — `rowStyle` returning `{ background: "transparent" }` for every non-special row (as `InvoiceRegisterPage`'s "highlight Overdue rows" logic originally did) silently killed hover on that page while `CustomerListPage`/`POSProfileListPage` (which don't pass `rowStyle`) worked fine. A `rowStyle` callback must return `null`/`undefined` for the common case and only return a style object for the actual exception (e.g. `status?.startsWith("Overdue") ? { background: ... } : null`).
- **`.pos-btn-danger` is a solid dark-red fill (`background: var(--color-danger-text)`, white text), not the light tinted `--color-danger-bg`/`--color-danger-text` pairing used for badges/alerts.** The tinted version reads as barely-there for a button (low contrast, easy to miss next to `pos-btn-primary`); reserve the tint pairing for passive elements (badges, alert banners) and use the solid fill for any actual destructive button (`Cancel Invoice`, `ConfirmModal`'s `danger` variant).
- **`SyncPage.jsx` is a UI-only placeholder, not a real integration.** Its doctype list, pending-change counts, "last synced" times, and recent activity feed are all hardcoded constants, and its Fetch/Upload buttons just `setTimeout` to fake a spinner — there is no RxDB/IndexedDB, no offline queue, and no actual sync engine anywhere in this codebase yet. Don't build against it as a real data source or wire new features to "the sync state"; it's a preview of the future offline-sync milestone (see the architecture roadmap in memory / README's Roadmap section). If asked to make sync "real," that's a substantial new feature (local storage layer + background engine), not a bug fix.
- **Held/parked sales are Draft-status Sales Invoices, not a separate "hold" concept.** `Cart/DraftPickerModal.jsx` lets a cashier park an in-progress cart by leaving the invoice in `Draft` status, then searches/filters Draft invoices (by customer, mobile, email) to pull one back into the terminal later. Follow this pattern (reuse Draft status + `DraftPickerModal`'s search) for any new held-sale/parked-sale feature rather than inventing a new status or separate storage.
- **PWA installability** (`posapp/vite.config.js`, `easy_pos/api/pwa.py`, `posapp/src/pwa/PwaUpdateBanner.jsx`) is implemented — installable manifest, precached app shell, prompt-to-reload update flow — but scoped strictly to static-asset caching, not the offline-first RxDB/sync architecture (that's still unbuilt, see the `SyncPage` gotcha above). Uses `vite-plugin-pwa` with `strategies: 'generateSW'`.
  - **Service worker scope vs. asset base**: the SPA is routed at `/posapp/*` but Vite's build output (and thus the natural `sw.js` location) is served from `/assets/easy_pos/posapp/*`. A worker's default scope is the directory it's served from, so a `sw.js` fetched from the assets path can't control `/posapp/*` pages. Frappe's `website_route_rules` wildcard + `StaticPage`'s refusal to serve `.js` files also rules out placing it under `easy_pos/www/posapp/`. Fixed by serving `sw.js` through a whitelisted API endpoint (`easy_pos.api.pwa.service_worker`, returns a raw `werkzeug.wrappers.Response` with a `Service-Worker-Allowed: /posapp/` header) and registering it manually via `workbox-window`'s `Workbox` class (not vite-plugin-pwa's `virtual:pwa-register`, which hardcodes the SW URL to the build `base` and can't point at a custom API endpoint).
  - Because the SW script is fetched from a non-standard location (`/api/method/...`), Workbox's relative precache/runtime URLs resolve wrong unless `inlineWorkboxRuntime: true` and `modifyURLPrefix: { '': '/assets/easy_pos/posapp/' }` are set, with an absolute `navigateFallback`.
  - The PWA manifest is a **static** `posapp/public/manifest.webmanifest` file (linked directly in `index.html`), with `manifest: false` in the VitePWA config — the plugin's auto-generated manifest/icon precache entries bypass `modifyURLPrefix` (confirmed by reading the plugin source) and 404, breaking SW install.
  - API responses must never be cached (cookie-based `sid` auth, shared terminal risk) — `workbox.runtimeCaching` has an explicit `NetworkOnly` rule for `/\/api\//`, on top of not precaching anything outside the built JS/CSS/HTML.
  - `posapp/index.html`'s `window.pos_boot = {{boot | tojson}};` line must **never** be wrapped in a JS string (e.g. `JSON.parse("{{boot | tojson}}")`) — Jinja's `tojson` emits raw unescaped double quotes, which breaks any surrounding string literal and causes a runtime `SyntaxError` on every page load. This has drifted/broken before; if a "missing `)` after argument list" error is reported on any `/posapp/*` page, check this line first.
- **Deep-linking a filtered list page**: no list page used URL query params before `InvoiceRegisterPage` gained a `customer` filter pre-set from the Cart's "View purchase history" link (`components/Cart/index.jsx`). The pattern: the source page navigates with `useNavigate()` to `<route>?<filterKey>=<value>&<filterKey>Name=<label>` (both id and display-label, since the label usually isn't derivable without another lookup); the destination page reads `useSearchParams()` once, only as the **initial value** of its existing `useState` filter (`useState(() => searchParams.get("customer") || "")`), not synced on every param change. This works with zero other plumbing as long as the list page's existing filter/fetch `useEffect` already re-runs off that state (it does on every list page following the [list-view page pattern](#conventions--gotchas-learned-the-hard-way) above). Reuse this pattern instead of `location.state` for any future "jump into a filtered list from elsewhere" feature — query params survive a page refresh/bookmark, `location.state` doesn't.
- **Product Bundle support is display-only on the frontend — the actual explosion is entirely ERPNext's, not this app's.** `easy_pos.api.item._get_bundle_item_codes`/`_attach_stock_and_rate` stamp an `is_product_bundle` flag onto every item the grid/search returns (checked against `Product Bundle.new_item_code`, disabled=0), and `easy_pos.api.item.get_product_bundle_contents` returns the bundle's component rows (item_code/item_name/qty/uom) purely for the cart line's expand-panel preview (`Cart/index.jsx`, fetched lazily per item_code into local `bundleContents` state) and `Items/index.jsx`'s "Bundle" badge. **No backend change was needed in `create_invoice`** — a bundle parent item goes through as a completely normal Sales Invoice Item row, and ERPNext's own `Sales Invoice.validate() → update_packing_list() → make_packing_list()` (fires whenever `update_stock=1`, which `create_invoice` always sets, independent of `is_pos`) auto-populates `packed_items` and deducts component stock. Don't add bundle-explosion logic to `create_invoice`; if the flow needs to change, it's almost certainly a frontend-only or ERPNext-config change.
  - **Every component item inside a Product Bundle must NOT have `has_serial_no`/`has_batch_no` set**, or checkout throws `"Serial No / Batch No are mandatory for Item X"` — `make_packing_list` doesn't prompt for serial/batch on packed rows the way it does for a directly-added cart line (there's no UI for it), so a bundle can only safely contain serial/batch-tracked components once that gap is addressed; pick plain stock items when building/testing a bundle in the meantime.
  - `InvoiceDetailPage.jsx` shows a submitted invoice's exploded components in a "Bundle Components" table block (columns: `parent_item`, `item_code`, `qty`, `uom`, `warehouse`) sourced straight from `invoice.packed_items` — `fetchInvoice` (`frappe.client.get`) already returns this child table with no extra fetch needed, and the block is only added when `packed_items.length` is truthy.
- **Barcode scanning (hardware scanner + camera) both feed the same `searchText` field instead of duplicating the add-to-cart logic.** `hooks/useBarcodeScanner.js` is a reusable global-`keydown` hook that detects a keyboard-wedge hardware scanner's fast keystroke-burst-then-Enter pattern (buffered via inter-key timing, default `maxKeyIntervalMs: 50`) anywhere on the page, but only while focus is **not** on an editable element — this lets a cashier scan without clicking into the search box first, while manually typing into a focused field (e.g. the topbar search box itself) keeps working exactly as before via native input handling instead of being double-processed. `common/BarcodeScannerModal.jsx` is the camera equivalent — a reusable `Modal` wrapping `@zxing/browser`'s `BrowserMultiFormatReader.decodeFromVideoDevice` (a new dependency; no barcode-decoding library existed before). Both feed a scanned/detected code into `POSTerminalPage.jsx`'s existing `searchText` state, so it goes through `Items`' existing debounce/match/auto-add pipeline (`AUTO_ADD_MATCH_TYPES` in `components/Items`) exactly like a manually-typed search — no separate cart-adding code path. Reuse both the hook and the modal as-is for any future page that needs to react to a scan (e.g. stock-take/receiving), rather than reimplementing scan detection.
- **Item variant selection**: the grid/search (`easy_pos/api/item.py`'s `get_items`/`search_item`) now includes variant templates (`Item.has_variants=1`) but excludes individual variant Items (`Item.variant_of` set) from browsing — a variant is only reachable by picking its template's attributes. A new whitelisted `get_item_variants(template_item_code)` returns the template's attributes (in the template's own `Item Variant Attribute` child table order) with only the values that actually appear across its existing variants (not every value the `Item Attribute` master defines), plus each variant's own resolved stock/rate and its attribute values. `components/Items/ItemVariantModal.jsx` (opened by `Items/index.jsx` when a card or an exact-match scan/search resolves to a `has_variants` item) renders one row of chip buttons per attribute, disabling any value that wouldn't leave at least one variant still matching the rest of the current selection, and once exactly one variant matches shows its price/stock/qty stepper for Add to Cart — same `addItem` cart-store call as a normal item, just sourced from the resolved variant's `item_code`/`rate` instead of the card's own (a template's `stock`/`rate` are always `None`, same convention as "not priced yet").
  - **`Item.variant_of` is `NULL` in the DB for non-variant Items, not `""`**, even though it's a Link field — `filters={"variant_of": ""}` (or a query-builder `Item.variant_of == ""`) silently matches nothing on a plain `= ''` comparison and excludes every item, template included. Use `["is", "not set"]` in a `frappe.get_all`/`get_list` filters dict (Frappe's own NULL-or-empty fallback handling) or `IfNull(Item.variant_of, "") == ""` in a query-builder query instead. This bit the first pass of this feature — `search_item`'s exact `item_code` match returned normally, but every browse/fuzzy-search path came back empty.
  - **`Topbar`'s search box only shows the camera-scan trailing icon when a page passes `onScanClick` through `setTopbar`, and `AppLayout.jsx`'s `DEFAULT_TOPBAR` object is an explicit allowlist of which `setTopbar` keys actually reach `<Topbar>`.** Adding a new topbar-configurable prop (like `onScanClick`) requires adding it to `DEFAULT_TOPBAR` *and* forwarding it in the `<Topbar ... />` JSX in `AppLayout.jsx` — passing it from the page alone silently does nothing, since `AppLayout` only spreads the known keys through. This bit the first pass of the camera-scan button (button didn't render until both spots were updated); check `AppLayout.jsx` first if a new `setTopbar` field appears to have no effect.
- **Receipt Delivery (Email/SMS Notifications)**: two new POS Profile custom fields, `ep_email_notification`/`ep_sms_notification` (both `Link` to Frappe's own `Notification` doctype, added via `easy_pos/patches/add_pos_profile_receipt_notifications.py`, `insert_after: print_format`), let a cashier pick a pre-configured Email-channel and/or SMS-channel Notification per profile. `POSProfileDetailPage.jsx`'s "Receipt Delivery" card renders both as `LinkField`s pre-filtered with `filters={[["Notification", "channel", "=", "Email"]]}` (or `"SMS"`) so only same-channel Notifications are pickable. `easy_pos.api.pos.create_invoice` calls `send_receipt_notifications(sales_invoice, pos_profile)` right after `sales_invoice.submit()`, which just does `frappe.get_cached_doc("Notification", name).send(sales_invoice)` for each configured field — **don't reimplement recipient resolution or message rendering**, `Notification.send()` already does it (its `recipients` child table's `receiver_by_document_field` reads straight off the Sales Invoice, e.g. `contact_email`/`contact_mobile`; actual delivery goes through Frappe's own email queue / SMS Settings gateway). Wrapped in try/except so a bad/misconfigured Notification can never block checkout. WhatsApp delivery is not implemented — would need a separate gateway integration.
- **Cashier Reports & Dashboard** (`posapp/src/pages/ReportsPage.jsx`, reached via the Sidebar's "Reports" item, no longer `comingSoon`): a single whitelisted method, `easy_pos.api.pos.get_sales_report(scope, opening_entry, pos_profile, from_date, to_date)`, backs all three scopes (Shift / Today / a custom date Range) — it's always scoped to `frappe.session.user`'s own invoices (never another cashier's), aggregating Sales Invoice/Sales Invoice Item/Sales Invoice Payment rows via `frappe.qb` (no raw SQL) into KPI totals, a payment-method breakdown, an hourly (Shift/Today) or daily (Range) sales trend, top-selling items, discounts/returns, and recent transactions. The Shift scope's payment summary **reuses `get_closing_entry` directly** (calling the existing Python function, not re-deriving the payment-mode-grouped query) rather than duplicating it — if `get_closing_entry`'s shape changes, `get_sales_report`'s `shift_summary` key changes with it. A second endpoint, `get_past_shifts`, lists the cashier's own **closed** `EP Opening Entry` records (`ep_closing_entry` set) so the Shift scope isn't limited to the currently-open shift — `ReportsPage.jsx` shows a shift picker (defaulting to the open shift if there is one, else the most recent past one) so a cashier can review any past shift's X/Z-style summary, not just a live one.
  - **Charting uses `frappe-charts` (already a dependency of the Frappe framework itself, pinned to the same `2.0.0-rc27` version), not a new charting library** — `common/Chart.jsx` is a thin React wrapper (`new Chart(container, { data, type, height, colors, ...options })` in a `useEffect`, destroyed/rebuilt on data change) reusable for any future bar/line/pie/percentage chart. `common/StatTile.jsx` (KPI tile with a colored icon badge) and `common/ReportCard.jsx` (titled `pos-card` section wrapper with a hover lift, `.pos-card-interactive`) are the other two new common components this feature introduced — reuse all three for any future report/dashboard work instead of hand-rolling.
  - **`TextField`/`DateField`'s `onChange` callback receives the raw value directly, not an event** — wiring it as `onChange={(e) => setter(e.target.value)}` (the native-DOM-event pattern) throws (`e.target` is `undefined`) and silently reverts the field since the exception aborts the state update. Always wire these as `onChange={setter}` or `onChange={(value) => ...}`.
  - **A field placed inline next to plain elements (chips, buttons, text) in the same flex row needs `.pos-field`'s default `margin-bottom: 14px` reset**, or `align-items: center` centers the field's padded outer box instead of the visible input, throwing off alignment against a sibling with no such margin (the general version of this gotcha — margin winning over `align-items` — is documented above under `FieldShell`). Fixed here with a reusable scoped rule, `.pos-inline-fields .pos-field { margin-bottom: 0; }` (`theme/components.css`), applied to the wrapping div rather than the field's own `className` (which only reaches the inner input, not the outer `.pos-field`).
  - **`ChildTable`'s forced `minWidth = max(columns.length * 110, 480)` (meant for full-width tables) causes horizontal scrolling inside a narrow card** — e.g. a 3-column table in a two-up `minmax(300px, 1fr)` grid cell. `ReportsPage.jsx`'s "Shift summary" and "Top selling items" cards use custom compact flex-row layouts instead (colored-dot rows; a ranked list with `.pos-rank-badge` + `.pos-progress-track`/`.pos-progress-fill`) rather than `ChildTable`, reserving `ChildTable` for the full-width "Recent transactions" card where it fits without scrolling. Check a `ChildTable`'s actual rendered width in its target layout before reusing it in a narrow card.
  - Every page routed through `AppLayout` must call `setTopbar(...)` in a `useEffect` on mount, even just `setTopbar({ title: "..." })` — `AppLayout`'s topbar state is shared across route changes and only resets the fields a page explicitly passes (merged onto `DEFAULT_TOPBAR`), so a page that never calls it keeps showing whatever title/search box the previously visited page left behind. This bit the first pass of `ReportsPage.jsx` (kept showing "Invoices" and its search box after navigating from `/posapp/invoices`).
- **Real Payment Integration (Payment Gateways)**: `InvoicePay/index.jsx`'s manual "type the amount received" flow now has a live-gateway path alongside it, built as a **pluggable gateway abstraction** rather than a Razorpay-specific integration, so adding Stripe/PayPal/etc. later never touches `InvoicePay`. Backend: `easy_pos/api/payment_gateways/` is a package whose `__init__.py` holds a `GATEWAYS` registry (name → module); each module (e.g. `razorpay.py`) implements `get_config()`, `create_order(sales_invoice, amount)`, and `verify(sales_invoice, payload) -> reference_id`. Three gateway-agnostic whitelisted endpoints in `easy_pos/api/payment.py` (`get_payment_gateway_config`, `create_payment_gateway_order`, `verify_payment_gateway_order`) dispatch through that registry, reusing `_save_sales_invoice`/`_finalize_invoice` (extracted from `easy_pos/api/pos.py`'s `create_invoice` — the same helpers a normal checkout uses) so a gateway checkout produces the exact same Draft/submit shape a manual one would. Frontend mirrors this: `posapp/src/components/PaymentGateways/` has `index.js` (a `getPaymentGateway(name)` registry) and one module per gateway (`razorpay.js`) implementing a common `{ name, pay(ctx) }` interface — `pay()` resolves with the finalized Sales Invoice dict, or rejects with `{ cancelled: true }` (modal dismissed — not an error) or an `Error` with a user-facing message. `InvoicePay/index.jsx` only ever reads `POS Payment Method.ep_payment_gateway` (a `Select` custom field — options are gateway names, added via `easy_pos/patches/add_payment_gateway_fields.py`, `insert_after: ep_automatically_calculated`) to find which row is gateway-backed, fetches that gateway's config to check it's actually configured (the Select being set doesn't mean credentials exist), and calls `getPaymentGateway(name).pay(...)` — it has no gateway-specific code at all. **To add a new gateway**: add its name to the Select's `options` in the patch, add a module implementing the three backend functions + registry entry in `payment_gateways/__init__.py`, and a module implementing `{ name, pay }` + registry entry in `PaymentGateways/index.js` — nothing else changes.
  - The cart is saved as a **Draft** Sales Invoice (via `_save_sales_invoice`) before the gateway checkout even opens, and only submitted (`_finalize_invoice`) once `verify_payment_gateway_order` confirms the charge — this deliberately reuses the same Draft-invoice-as-intermediate-state convention as held/parked sales (`Cart/DraftPickerModal.jsx`), so a dismissed or failed gateway payment just leaves a normal retrievable Draft rather than needing separate failure-state handling.
  - Razorpay's module (`easy_pos/api/payment_gateways/razorpay.py`) wraps the `payments` app's existing `Razorpay Settings` doc (already installed on this bench) for order creation — reusing its rupee→paisa conversion and credential storage rather than re-implementing them — but does its **own** Checkout.js client-callback signature verification via the official `razorpay` Python SDK's `client.utility.verify_payment_signature`. This is deliberately distinct from `RazorpaySettings.verify_signature`, which is for the async webhook payload, not the client-side `handler` callback Checkout.js invokes after payment.
  - Frappe's `Payment Request`/`Integration Request` doctypes (the framework's built-in e-commerce-style payment orchestration, `erpnext/accounts/doctype/payment_request/payment_request.py`) were deliberately **not** used here — `make_payment_request`'s `get_payment_url()` redirects to a server-rendered hosted checkout page (`payments` app's `razorpay_checkout.html` template), which doesn't fit embedding Razorpay's Checkout modal directly inside this React SPA. Calling `Razorpay Settings`' `create_order`/Checkout.js/`verify_payment_signature` directly, as done here, is the right pattern for an SPA-embedded gateway checkout; reach for `Payment Request` instead only if a future gateway integration genuinely needs an emailed/redirect-based payment link flow.
  - Razorpay's Checkout.js (`posapp/src/components/PaymentGateways/razorpay.js`) is loaded from Razorpay's own CDN (`https://checkout.razorpay.com/v1/checkout.js`) at runtime, not bundled — there's no npm package that's the source of truth for it, and vendoring would silently drift from Razorpay's own fraud/3DS updates.
  - Test-mode Razorpay credentials come from the merchant's own Razorpay Dashboard (Test Mode toggle → Settings → API Keys) — there's no way to fabricate working keys; Razorpay's publicly documented test values (`4111 1111 1111 1111` success card, `4000 0000 0000 0002` failure card, `success@razorpay`/`failure@razorpay` test UPI handles) are safe to use against real test-mode keys for verifying both the success and the dismissed/failed paths.
  - **`InvoicePay/index.jsx`'s auto-print receipt tab must be opened with `window.open()` synchronously inside the actual button-click handler, never inside an async callback fired later** (a `.then()`, a `postMessage` handler, Razorpay's `handler` callback, etc.) — browsers only treat `window.open()` as user-gesture-initiated (and thus exempt from the popup blocker) if it's still on the call stack of the original click/keydown event; any await or event-loop turn in between loses that "user activation" silently, with no error, no console warning, just a `null` tab. This bit `payWithGateway()` once already: it used to open the receipt tab from inside Razorpay's `handler` (fired via postMessage from the Checkout iframe, several turns removed from the "Pay with Razorpay" click) to avoid focus-yanking the cashier away from the still-open Razorpay modal — worked as *code*, but got silently popup-blocked in real browsers, so cash checkouts printed fine and gateway checkouts never did. Fixed by opening the tab (with a "Finishing up…" placeholder, later updated via `receiptTab.location.href` once `finishCheckout` has the invoice name — same as the manual flow) synchronously at the top of `payWithGateway()` itself, immediately followed by `window.focus()` to address the original focus concern instead of delaying the `window.open()` call. Apply this same synchronous-open-then-navigate-later pattern to any future gateway module's `pay()` flow.
- **Customer-Facing Second-Screen Display**: targets the standard dual-monitor till setup — a second monitor plugged into the *same* register PC, not a separate tablet/device (that would need a real backend transport instead of same-browser messaging). A new POS Profile checkbox `ep_customer_display_enabled` (`easy_pos/patches/add_pos_profile_customer_display.py`) gates a "Customer Display" icon button in `Cart/index.jsx`'s header that `window.open`s `/posapp/customer-display` (a named window, so re-clicking focuses the existing one instead of duplicating it).
  - `posapp/src/utils/customerDisplayChannel.js` wraps the `BroadcastChannel` API (same-origin, same-browser, zero backend) behind a tiny `send`/`subscribe` pub-sub interface, with the channel scoped per POS Profile (`easy-pos-customer-display-<pos_profile>`) so two profiles open on the same machine don't cross-talk. Kept behind this one module so a future "separate device" mode (Frappe realtime/socketio instead of `BroadcastChannel`) only requires swapping this file's internals, not the Cart/CustomerDisplayPage code that uses it.
  - `posapp/src/hooks/useCustomerDisplayBroadcaster.js`, mounted once in `Cart/index.jsx`, mirrors the exact totals Cart already shows by reusing its `computeCartTotals` (`utils/tax.js`) call — no duplicated tax logic on the display side. It sends `CART_UPDATE`/`CART_IDLE` reactively off cart-store changes, and exposes `sendPaymentStatus`/`sendInvoiceComplete` for Cart to call explicitly at the payment-start and checkout-complete points (these aren't derivable from store state alone). It also answers a `HELLO` message from the display page with an immediate resend of the current snapshot, so a display window opened or reloaded mid-sale isn't stuck blank until the next cart change.
  - `InvoicePay/index.jsx` gained an `onComplete({ invoiceName, grandTotal, amountPaid, changeDue })` prop, called from `finishCheckout` (its single completion point for both the manual and gateway-confirmed payment paths) right before `resetCart()`/`onClose()` — this is how the broadcaster learns the finalized paid/change amounts, since neither is otherwise available outside `InvoicePay`.
  - `posapp/src/pages/CustomerDisplayPage.jsx` is a presentational-only kiosk view (`RequireAuth` + `LoadOpeningEntry`, but **no** `AppLayout`/sidebar — a bare full-bleed route added as a sibling to the main `AppLayout` route group in `routes.jsx`) with an `idle | cart | payment | complete` state machine, rendered via `components/CustomerDisplay/{IdleScreen,CartView,PaymentView,ThankYouScreen}.jsx`. It needs its own `LoadOpeningEntry` (not just `RequireAuth`) because it's a second window with its own separate `posSessionStore` instance — Zustand state is per-JS-runtime/per-tab, so `posProfile` (needed to pick the right BroadcastChannel) has to be independently loaded via `checkOpeningEntry`, not inherited from the Terminal window.
  - **`resetCart()` (called right after invoice completion, before `onClose()`) fires its own `CART_UPDATE`/`CART_IDLE` broadcast a beat after `INVOICE_COMPLETE`**, since the cart-items-changed effect in the broadcaster hook doesn't know a checkout just finished — left unhandled, this instantly stomps the thank-you screen with the idle view. Fixed by having `CustomerDisplayPage` track the current view in a ref (`viewRef`, kept in sync by a small `setView` wrapper) and ignore `CART_UPDATE`/`CART_IDLE` messages while showing `complete` — the thank-you screen's own `setTimeout` is what's allowed to transition it back to idle. Any future message type added to this channel needs the same guard if it can fire in the same tick as (or right after) `INVOICE_COMPLETE`.
